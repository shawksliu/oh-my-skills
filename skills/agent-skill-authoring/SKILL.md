# 高性能 Agent Skill 撰写指南 (Agent Skill Authoring Guidelines)

本规程总结了构建高执行力、防作弊、闭环型 Agent Skill 的核心实战心法。**拒绝写出“表面排版整洁、实际一碰就偷懒”的形式主义规则**。

---

## 核心反思：为什么传统规则经常失效？

传统的标准模板往往陷入以下三大误区：
1. **形式主义**：充斥着满篇大写的 `MUST` / `NEVER` 和漂亮表格，看似规范，实际上 Agent 只会机械填充。
2. **缺乏防作弊机制**：假设 Agent 会自觉执行（例如假设 Agent 截图后真的看了），忽视了 LLM 倾向于“调了工具却不看结果”或“发现 Bug 直接当成总结呈报”的懒惰本性。
3. **僵化一刀切**：对微小修改也要求走全套繁重流程，导致 Agent 产生逆反心理，直接跳过整个 Skill。

---

## 高级 Skill 撰写五大心法

### 1. 动机驱动而非死板命令 (Theory of Mind)
* **核心动作**：在 Skill 开头务必增加 `这个规程要解决什么问题` 或 `为什么要这么做`。
* **效果**：现在的 LLM 非常聪明，理解了动作背后的逻辑（例如“把‘觉得没问题’换成‘真的看过’”）后，自发遵循度会远高于死板的禁令。

### 2. 精准对抗作弊与敷衍 (Anti-Task-Evasion)
针对 Agent 常见的作弊套路，必须设置硬性“抓手”：

| Agent 偷懒套路 | 规程中的精准破解抓手 |
| :--- | :--- |
| **调了工具但不看结果**（如截图存了盘但没看） | **强制显式思考链**：要求“必须使用查看工具打开，并写下你在图中实际看到了什么”。 |
| **发现 Bug 直接在总结里交差** | **硬性闭环约束**：明确“发现问题先修复，修复后重新验证，循环到通过为止。禁止直接写进交付说明当结项”。 |
| **伪造全绿结果** | **鼓励真实过程**：要求记录“发现 XX ➔ 已修复 ➔ 重新验证通过”，强调真实调试过程比好看的全绿清单更有说服力。 |

### 3. 弹性分级机制 (Tiered Execution)
* **核心动作**：将执行流程划分为 **轻量级 (Lightweight)** 与 **完整级 (Comprehensive)**。
* **准则**：
  * **轻量级**：针对范围明确、无破坏性的微调（如改文案、改单属性颜色），仅需核心步骤。
  * **完整级**：针对新功能、布局调整、架构改动，走全套死循环校验。
* **价值**：避免因为“流程太重”导致 Agent 在小任务中敷衍或引发反向对抗情绪。

### 4. Trigger Description 必须极具 Push 属性
* **核心动作**：在 SKILL.md Frontmatter 的 `description` 中，明确加入**防御性触发词**。
* **写法示例**：*“...当处理 XX 任务时使用此规程，即使用户没有明确要求 'XX' 或 'YY'，也必须触发。”*
* **价值**：LLM 普遍存在 Undertrigger（能不用就不用）的倾向，Push 属性能够显著提升 Skill 的触发精准度。

### 5. 抓手明确，不给模糊空间 (Definite Instructions)
* 避免写“请仔细检查视觉效果”这种模糊空话。
* 必须写“检查 Flex/Grid 对齐是否有 1px 错位；检查 375px/1440px 宽度下是否有横向滚动条”。

## 撰写 Skill 时的 Check-List (自我审查)

在输出任何 Skill.md 之前，问自己以下 4 个问题：

- [ ] **它懂 Agent 的偷懒小动作吗？**（是否防范了“只调工具不看结果”、“把 Bug 当总结汇报”等套路？）
- [ ] **它解释了 Why 吗？**（是否让 Agent 明白了这个规程的目标是什么？）
- [ ] **它有分级机制吗？**（修改 1 个字和重构整个页面，流程是否有所区分？）
- [ ] **描述够 Push 吗？**（当用户没有明说要验证时，它还能触发吗？）
