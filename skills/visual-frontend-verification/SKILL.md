# 前端与视觉验证规程

## 这个规程要解决什么问题

"代码改完了,终端也没报错"只说明语法过关,不代表效果是对的。CSS 错位、响应式断点崩溃、状态切换时的视觉问题,只有渲染出来亲眼看过才能发现。这份规程只有一个目的:把"我觉得应该没问题"换成"我真的看过,而且看到的和预期一致"——发现问题也不能绕过去,要修复到真正通过为止。

## 核心原则

1. **视觉证据优先于代码逻辑**:构建无报错只是语法关卡,不是验收标准。凡是视觉相关的改动,必须实际渲染出来、截图,并且亲自用查看工具看过这张图再下判断——不能靠"这段 CSS 按理说会这样显示"来代替看。
2. **发现问题就地解决,不是记录了事**:审查中任何一项不符合预期(错位、溢出、状态缺失、切换后看不清等),先尝试修复,改完之后回到截图这一步重新验证,如此循环,直到这一项真正通过。只有遇到你确实无法自行判断或解决的阻塞(比如需要用户提供缺失素材、或者需要用户做设计取舍决定)时,才可以带着清楚的说明去问用户——而不是自己觉得"问题不大"就放过。
3. **验证力度要和改动匹配**:不是每次改动都要走全套流程,见下方分级。

## 验证力度怎么选

**轻量验证** —— 适用于单一样式属性微调(颜色、间距、字号、文案等)、影响范围清晰局限在一个已验证过的组件内、不涉及布局结构调整、不引入新的交互状态。
只需要:渲染/刷新 → 截取改动所在位置的截图 → 用查看工具确认改动确实生效、周边没有明显破坏 → 完成。

**完整验证** —— 适用于新增组件、布局调整、响应式相关改动、新增或修改交互状态、影响共享/复用组件的改动,或者你自己也不确定这次改动影响范围有多大的时候。走下面的完整流程。

拿不准时默认走完整验证,但不要为了显得严谨,对一行样式改动也搬出全断点扫描——那只是走过场,不是真验证。

## 完整验证流程

**Step 1 — 渲染与构建检查**
启动/刷新本地渲染环境,确认控制台没有阻断性报错或关键资源缺失。

**Step 2 — 截图并且真的去看(这一步不能跳过)**
对改动涉及的页面/组件截图。截图生成之后,用查看工具把它打开,写下你在图里实际看到的内容,再拿这个和下面的审查表逐项对照——不能截了图就默认"应该没问题",必须真正看过。

**Step 3 — 多维度审查**

| 维度 | 核对点 |
| :--- | :--- |
| 布局 | Flex/Grid 对齐是否合理、有没有明显错位或溢出;间距是否符合预期 |
| 配色与模式切换 | 深色/浅色模式下文字是否都清晰可读,颜色是否和预期一致 |
| 排版 | 字体、字号、行高是否正常加载;长文本/极端文本下有没有异常换行或溢出 |
| 响应式 | 常见断点(如手机/平板/桌面宽度)下有没有破损或意外横向滚动条 |

**Step 4 — 交互与动态状态**
触发 hover / active / focus 等状态,确认视觉反馈符合预期;检查过渡动画是否流畅、没有闪烁;数据更新或异步加载时,确认没有明显的布局跳动。

## 发现问题之后

不通过的项目,先修复,再回到 Step 2 重新截图验证,循环到通过为止。不要把"发现的问题"直接写进交付说明就算完成——那等于什么都没做。真正卡住你的、需要用户输入信息或做决定的情况,才说明清楚去问用户。

## 交付

把实际截图作为证据交给用户(具体用什么方式提供,由你根据当前环境判断),附上简要的验证记录——哪些检查做了、结果如何。如果中途发现过问题,如实写"发现 XX → 已修复 → 重新验证通过",而不是让清单看起来一次性全绿——真实的过程比好看的清单更有说服力。
